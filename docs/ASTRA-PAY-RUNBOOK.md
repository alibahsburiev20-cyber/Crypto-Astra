# Astra Pay: что делать, когда что-то пошло не так

Этот файл читают в момент аварии, поэтому здесь нет теории — только «симптом →
действие». Все команды админки вызываются с заголовком `X-Admin-Token`.

## Золотое правило

**Сначала остановить выплаты, потом разбираться.** Стоп ничего не ломает:
игроки продолжают играть, балансы остаются, заявки ждут. Ошибочная выплата
необратима, а остановка — обратима.

```
POST /admin/pay/stop   { "stop": true, "reason": "сверка: расхождение" }
```

Снять стоп: `{ "stop": false, "reason": "разобрались" }`.

## Симптомы

### 1. Ночная сверка нашла расхождение

Сверка сама поднимает стоп-флаг и пишет в логи `pay reconcile mismatch`.

**Что делать:**
1. `GET /admin/pay` — посмотреть `reconcile.issues`.
2. `ledger_broken` → журнал правили в обход кода. Сравнить `pay_ledger.hash` с
   цепочкой, найти последнюю целую запись. Не «лечить» — восстановить из бэкапа
   D1 (Time Travel) и разобраться, кто имел доступ.
3. `deposits_vs_ledger` → есть зачисленный депозит без записи в журнале (или
   наоборот). Сверить по `txid` в explorer, дописать недостающее **новой**
   записью с `reason = adjust` и `idem_key = fix:<txid>`.
4. `payouts_vs_withdrawals` → выплата без заявки или заявка без выплаты.
   Проверить `pay_payouts` и `pay_withdrawals` по `txid`.
5. `negative_balance` → покупка прошла при недостатке денег. Заблокировать
   игрока от покупок, вернуть баланс компенсирующей записью.

Стоп снимается только после того, как `issues` пуст.

### 2. Заявка «зависла» в `broadcasting`

**Что делать:**
1. Взять `txid` из `GET /admin/pay` (`queue`), открыть в обозревателе сети.
2. Транзакция есть и подтверждена → `POST /admin/pay/withdrawal`
   `{ "id": "...", "action": "sent", "txid": "..." }`, затем `confirm`.
3. Транзакции нет → `action: "fail"` с причиной. Деньги вернутся на баланс
   компенсирующей записью, игрок сможет подать заявку снова.
4. Не отправлять повторно «на всякий случай»: `txid` уникален, но два перевода
   в сеть уйдут как две разные транзакции — это и есть двойная выплата.

### 3. Депозит не пришёл

Помнить главное: **отсутствие события у индексатора — не доказательство, что
платежа не было.** Смотреть в explorer по адресу игрока.

1. Проверить контракт: переводили ли настоящий USDT, а не «похожий» токен.
2. Проверить `contractRet` — неуспешная транзакция денег не приносит.
3. Проверить адрес: совпадает ли с `GET /pay/address.json` этого игрока
   (адрес постоянный, меняться не должен).
4. Если перевод есть, а события нет — это дыра в мониторе. Зачислить вручную
   нельзя (API этого не умеет) — значит, чинить монитор и перезапускать
   `applyDeposits`, он подберёт событие по `(txid, event_index)`.

### 4. Signer недоступен

`503 signer_not_configured` или `502 signer_*`.

Это безопасное состояние: деньги не двигаются, заявки копятся в `reserved`.
Ничего не «объезжать» — ключ есть только у Signer. Проверить секреты в
дашборде и биндинг `SIGNER` в `wrangler.toml`.

### 5. Подозрение на утечку ключа горячего кошелька

1. `POST /admin/pay/stop` — немедленно.
2. Вывести остаток из горячего кошелька в холодный (вручную, из кошелька).
3. Заменить `SIGNER_PRIVATE_KEY` в секретах Signer на новый ключ.
4. Поднять лимиты выплат заново только после разбора.

Семя адресов (`SIGNER_SEED`) менять **нельзя**: вместе с ним исчезнут все
адреса игроков. Оно хранится отдельно от ключа выплат именно поэтому.

### 6. D1 недоступна или лимит записей

Платежи встают, игра продолжается (мир живёт в Durable Objects).
Монитор и сверка отключаются сами (ошибки в логах), стоп-флаг выплат — поднять
вручную. Ждать сброса лимита, ничего не «дописывать» в обход.

### 7. Выплата встала с `signer_contract_mismatch` / `chain_id_mismatch` / `nonce_busy`

| Код | Что это значит | Что делать |
|---|---|---|
| `signer_contract_mismatch` | `PAY_EVM_CONTRACT*` (Worker) и `SIGNER_EVM_CONTRACT*` (Signer) разошлись | привести к одному в **этой** сети (у Polygon свои имена с `_POL`), деплой Signer; деньги не двинулись |
| `contract_misconfigured` (у Signer'а) | для сети нет allowlist-контракта: `SIGNER_EVM_CONTRACT_POL` пуст | задать контракт этой сети; «взять общий с BNB» нельзя — подписать чужой токен Signer не должен |
| `chain_not_allowed` (у Signer'а) | `chainId` транзакции нет в `SIGNER_EVM_CHAIN_IDS` | добавить число этой сети (Polygon — `137`, Amoy — `80002`) и передеплоить Signer |
| `chain_not_evm` | выплату попытались провести через EVM-транспорт не-EVM-цепью | это про конфигурацию, а не про данные: сверь `PAY_CHAIN`/`PAY_EVM_CHAINS` |
| `chain_id_mismatch` | нода обслуживает не ту сеть, для которой готовилась транзакция | сменить `PAY_EVM_RPC` на свою/проверенную; не «пробовать ещё раз» |
| `gas_price_too_high` | нода посоветовала газ дороже `PAY_MAX_GAS_PRICE_WEI` | подождать или поднять потолок осознанно; заявка осталась `reserved` |
| `hot_wallet_no_bnb` | на кошельке хватает USDT, но нет BNB на газ | занести BNB (0.0005 достаточно на десятки переводов) |
| `nonce_busy` | параллельная отправка заняла этот номер | ничего: повторить через минуту, замок сам освободится при ошибке |
| `hot_address_mismatch` | `PAY_HOT_ADDRESS` — не тот ключ, что в Signer | исправить `PAY_HOT_ADDRESS`; проверять надо до того, как на кошелёк упадут деньги |

Заявка во всех этих случаях остаётся в прежнем состоянии: `reserved`. Резерв
списан с баланса игрока, деньги не удвоены и не потеряны — `fail` возвращает их
компенсирующей записью.

## Переезд на EVM-сеть (BNB Chain, затем Polygon): порядок действий

Сетей две, и включаются они **независимо**: BNB и Polygon — один код, но разные
контракты, RPC, подтверждения и шкала USDT (18 против 6 знаков). Порядок ниже
проходится отдельно для каждой; всё, что отличается, собрано в конце раздела.

1. Завести свою ноду или проверить публичный RPC: `eth_chainId` должен быть `56`.
2. Включить `PAY_EVM_CONTRACT` (mainnet — `0x55d398326f99059ff775485246999027b3197955`,
   Binance-Peg BSC-USD; **18 знаков**, это не тот USDT, что в TRON).
3. Тот же контракт — в секрет `SIGNER_EVM_CONTRACT`, `SIGNER_EVM_CHAIN_IDS = "56"`. Деплой Signer.
4. `PAY_HOT_ADDRESS` = `0x`-форма того же горячего ключа:
   `SIGNER_PRIVATE_KEY=<hex> npm run pay:hot-address -- --check <адрес> --chain bsc`
   печатает обе формы и не даёт оставить в конфиге адрес прошлой сети.
   Завести на неё USDT и BNB.
5. Миграция `0008_pay_addresses_chain.sql`: у адреса появляется сеть. Без неё
   второй адрес игроку деть некуда (`user_id UNIQUE` на всю таблицу), и
   переключение цепи означало бы «приём стоит». На проде применять её не
   обязательно: `ensurePaySchema` перестраивает таблицу сам, в том числе на
   непустой — строки переносятся (сеть берётся из формата адреса: `0x…` → `bsc`,
   `T…` → `tron`), `address`, `hex`, `derivation_index`, `active` и курсор
   монитора остаются нетронутыми, а пачка идёт одним `batch`, то есть одной
   транзакцией D1: «таблицу сняли, новую не создали» невозможно.
   Код останавливается и требует человека в одном случае: если в `address` лежит
   то, что нельзя отнести ни к одной известной сети (кто-то правил базу руками).
   Для базы с историей и бумажкой под рукой — `npm run db:migrate`
   (`wrangler d1 migrations apply DB --remote`), предварительно сняв дамп
   `d1 export`; локально — тот же файл без `--remote`.
   Проверка: `PRAGMA table_info(pay_addresses)` содержит `chain`, а
   `SELECT chain, COUNT(*) FROM pay_addresses GROUP BY chain` даёт то же число
   строк, что и до перестройки, и `/pay/status.json` отвечает `schema:"ready"`.
6. `PAY_CHAIN = "bsc"`, деплой. Дальше смотреть `/admin/pay`: строка `chain`
   показывает рельс (`ready`), курсор блока и сколько активных адресов относится
   к активной цепи (`addresses.otherChain` — сколько игроков ещё сидят на
   старых адресах; считается по колонке `chain`, а не по виду адреса).
7. Отдельного «перевыпуска» адресов не нужно: игрок, у которого в базе только
   TRON-адрес, при первом запросе `/pay/address.json` получает адрес BSC, а
   старый остаётся активным, пока на нём есть баланс (его забирает TRON-сбор —
   см. шаг 1 плана). `address_chain_mismatch` теперь означает не «сеть
   поменялась», а «метка в базе не сходится с адресом»: это ручная правка, и её
   чинят в базе, а не повторной попыткой.

### Вторая сеть: чем именно она отличается

| | BNB Chain | Polygon PoS |
|---|---|---|
| Контракт USDT (mainnet) | `0x55d398326f99059fF775485246999027B3197955` (18 знаков) | `0xc2132D05D31c914a87C6611C10748AEb04B58e8F` (USDT0, 6 знаков) |
| `chainId` прод / тестнет | 56 / 97 | 137 / 80002 |
| Подтверждений (прод / тестнет) | 15 / 3 | 64 / 12 |
| Имена переменных воркера | `PAY_EVM_CONTRACT_BNB` (или легаси `PAY_EVM_CONTRACT`), `PAY_EVM_RPC_BNB`, `PAY_EVM_CONFIRMATIONS_BNB` | `PAY_EVM_CONTRACT_POL`, `PAY_EVM_RPC_POL`, `PAY_EVM_CONFIRMATIONS_POL` |
| Секреты Signer | `SIGNER_EVM_CONTRACT_BNB`, сеть в `SIGNER_EVM_CHAIN_IDS` | `SIGNER_EVM_CONTRACT_POL`, `137` (и `80002` для тестнета) в `SIGNER_EVM_CHAIN_IDS` |
| Нативка на газ | BNB | POL |
| Потолок газа | 20 gwei по умолчанию — достаточно | по умолчанию **мало**: Polygon стоит 30–100 gwei, нужны `PAY_MAX_GAS_PRICE_WEI` и `SIGNER_EVM_MAX_GAS_WEI` ~100 gwei |

Общая переменная `PAY_EVM_CONTRACT` без суффикса относится **только к BNB** — это
историческое имя, а не «контракт по умолчанию для всех». Для Polygon она не
читается намеренно: подставить BSC-контракт в Polygon — это «скан ищет переводы
по токену, которого в сети нет», и выглядит оно как «игрок не заплатил».

Включение второй сети сводится к четырём строкам (`PAY_EVM_CHAINS=bnb,polygon`,
контракт, доменное имя переменной с `_POL`, сети в allowlist Signer'а) — и
прогону `npm run pay:rehearse -- --loopback --chain polygon`, который обязан быть
зелёным до того, как второй сети начнут обещать приём. Подробно — `docs/CHAINS.md`.

## Чего делать нельзя никогда

- Править `pay_ledger` и `pay_audit_log` — только новые записи.
- Повторять отправку выплаты без проверки `txid` в сети.
- Снимать стоп-флаг «чтобы работало», не разобравшись в причине.
- Хранить `SIGNER_SEED` или `SIGNER_PRIVATE_KEY` в D1, в репозитории или в браузере.

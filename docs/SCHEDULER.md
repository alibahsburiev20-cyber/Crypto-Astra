# Планировщик

У каждого Durable Object один alarm, поэтому все отложенные действия мира
хранятся в таблице `jobs` и обрабатываются одним планировщиком.

## Таблица jobs

| Поле | Смысл |
|---|---|
| `id` | UUID |
| `run_at` | когда выполнять (мс, серверное время) |
| `kind` | тип задачи |
| `payload` | JSON, обычно `{ expeditionId }`, `{ playerId }` или `{}` |
| `status` | `pending`, `done`, `failed` |
| `attempts` | число неудачных попыток |

Индекс `idx_jobs_due (status, run_at)`.

## Типы задач этапа 1

| kind | Когда ставится | Что делает |
|---|---|---|
| `expedition_finish` | старт рейса, на `ends_at` | награда, износ, опыт, очки, ресурсы, `completed` |
| `expedition_event` | старт и после выбора | открывает событие, переводит рейс в `waiting_choice`, ставит таймаут |
| `expedition_event_timeout` | при открытии события | применяет безопасный вариант, если игрок не выбрал |
| `fuel_regen` | создание игрока и после каждого тика | +1 топливо каждые 2 часа до бака |
| `ledger_verify` | создание игрока и после каждой проверки | сверка Ledger с балансами, заморозка при расхождении |
| `idem_cleanup` | при обслуживании | удаляет ключи идемпотентности старше 30 дней, чистит старые jobs |

`craft_finish`, `season_close`, `snapshot_export` появятся на следующих этапах.

## Будильник

- После каждого действия, меняющего очередь, `World.arm()` берёт
  `MIN(run_at)` среди `pending` и ставит alarm на это время.
- Если задач нет, alarm снимается.
- Уже стоящий более ранний будильник не отодвигается: `arm` сравнивает с
  `getAlarm()` и не перезаписывает его на более позднее время. Иначе задача,
  добавленная между чтением очереди и `setAlarm`, ждала бы следующего poke.
- `alarm()` вызывает `poke()`, который прогоняет все задачи с `run_at <= now`.

## Выполнение

`runDueJobs` (лимит 40 задач за проход):

1. В отдельной транзакции вызывает `ensureMaintenance`: ставит недостающие
   `ledger_verify`, `idem_cleanup` и `fuel_regen` игрокам.
2. Берёт ближайшую задачу `pending AND run_at <= now`.
3. В своей транзакции ещё раз проверяет, что задача всё ещё `pending`, выполняет
   её и ставит `done`. Если обработчик упал — транзакция откатывается.
4. При ошибке увеличивает `attempts` и ставит `run_at` по нарастающей паузе:
   30 с → 2 мин → 10 мин → 1 ч. После 5-й неудачи — `failed`.
5. Если задач больше лимита, остальные остаются `pending`, а alarm срабатывает
   сразу снова (их `run_at` уже в прошлом).

Задачи не «догоняют» друг друга внутри одной транзакции: каждая имеет свою.
Поэтому падение одной не откатывает уже начисленные награды.

## Cron

`worker/wrangler.toml`:

```
[triggers]
crons = ["0 * * * *", "0 3 * * *"]
```

`scheduled` каждый час:

1. Берёт список миров у `WorldLobby`. Если лобби недоступно — из зеркала
   `world_seats` в D1.
2. Вызывает `poke()` каждого мира: страховка, если alarm не сработал.
3. Чистит истёкшие refresh-сессии и старые счётчики частоты в D1.

Ежедневная выгрузка головы цепочки в R2 появится вместе с R2 (этап 2+).

## Диагностика

```sql
-- внутри мира (через Durable Object SQL, не D1)
SELECT status, kind, COUNT(*) FROM jobs GROUP BY status, kind;
SELECT * FROM jobs WHERE status = 'failed' ORDER BY run_at DESC LIMIT 20;
SELECT MIN(run_at) FROM jobs WHERE status = 'pending';
```

`failed` означает, что обработчик падал 5 раз. Причина — в логах Worker
(`job failed <kind> <error>`). Повторно запустить задачу можно, вернув её в
`pending` и поставив `run_at` в будущее; делать это только после исправления
причины и понимания, какие записи уже успели пройти.

# Прогон BSC-тестнета: адрес → депозит → покупка → выплата → подтверждение

Документ про один вопрос: **умеет ли рельс USDT BEP-20 проводить деньги целиком,
если дать ему настоящую сеть**. Код каждой части уже покрыт юнит-тестами
(`worker/test/unit/payEvm*.test.ts`, всего 118 кейсов на подставной ноде), но
ни один тест не касался реального RPC. Тестнет отвечает именно на «реальный».

Инструмент: `scripts/pay-bsc-rehearsal.ts` (npm-скрипт `pay:rehearse`). Правила,
по которым он говорит «сошлось» или «нет», вынесены в `scripts/lib/rehearse.ts`
и покрыты `worker/test/unit/payBscRehearseRules.test.ts` — их можно проверять без
сети, и в CI они проверяются.

## Два режима

| Режим | Что проверяет | Сеть |
|---|---|---|
| `--loopback` | склейку шагов: `eth_getLogs` → `pay_chain_events` → зачисление → покупка → заявка → подпись → отправка → квитанция → `confirmed` | не нужна, работает в CI |
| без `--loopback` | то же самое на настоящей ноде тестнета | нужен выход к `PAY_EVM_RPC` |

Ключевое удобство: оба режима зовут **одни и те же** боевые функции
(`scanEvmBlocks`, `applyEvmDeposits`, `buildPayoutTx`, `sendUsdtEvm`,
`verifyPayout`, `evmSweepPlan`) и **ту же** схему D1 (`ensurePaySchema`). Подставная
нода в `--loopback` отвечает так же, как настоящая — в том числе формой `txid`
(64 hex без `0x`), на которой чаще всего и спотыкается сверка.

## Быстрый прогон без денег (что угодно, кроме сети)

```bash
npm run pay:rehearse -- --loopback
```

Ожидаемый вывод: 39–41 строк `OK`, код выхода `2`. Двойка — это не ошибка: два
шага помечены `ПРОПУСК`, потому что в бою их делает не этот процесс (ключ подписи
живёт в Signer-контуре, а не в прогоне). Код `0` означал бы «проверено всё», `1` —
«есть расхождение».

## Прогон в тестнете: что нужно подготовить

1. **Своя сеть, свой токен.** Общего тестового USDT в BSC-тестнете нет, и
   фиксировать адрес «по умолчанию» нельзя: угаданный контракт = приём чужого
   токена за деньги. Поэтому `BSC_TESTNET.usdt` в `pay/evm/config.ts` — пустая
   строка, а `PAY_EVM_CONTRACT` обязан задать оператор. Задеплойте любой ERC-20
   с 18 знаками (`decimals() = 18`, `transfer(address,uint256)`) в BSC testnet —
   standard `Binance Testnet ERC20` подходит; адрес понадобится ниже.
2. **Тестовые BNB** — на «горячем» кошельке, он платит газ за отправку выплат
   ([faucet BNB Chain](https://www.bnbchain.org/en/testnet-faucet)). Игроку BNB не
   нужен: входящий перевод USDT оплачивает отправитель.
3. **Тестовые USDT** на адресе игрока: переведите себе 5 токенов с того же
   контракта (минимальный депозит в игре — 1 USDT, меньше зачислится не может).
4. Переменные окружения (только для прогона, **не** для прода):

```bash
export PAY_CHAIN=bsc
export PAY_NETWORK=testnet
export PAY_EVM_RPC=https://bsc-testnet-rpc.publicnode.com   # или своя нода
export PAY_EVM_CONTRACT=0x…                                  # адрес вашего токена
export PAY_EVM_CONFIRMATIONS=3
export PAY_HOT_ADDRESS=0x…                                   # тот же кошелёк, что и ключ
# ключ нужен ТОЛЬКО если зовёте --send; в бою он живёт в Signer и сюда не пишется
```

5. Прогон с ожиданием перевода (`--wait` — секунды; скрипт ходит на ноду, пока
   депозит не появится или таймер не кончится):

```bash
npx tsx scripts/pay-bsc-rehearsal.ts --blocks 3000 --wait 600
```

6. Настоящая отправка выплаты в тестнет (расходует ваши тестовые BNB на газ):

```bash
npx tsx scripts/pay-bsc-rehearsal.ts --blocks 3000 --send --hot-key <hex-ключ-тестнета>
```

`--send` **не работает при `PAY_NETWORK=mainnet`** — прогон оборвётся на шаге
«отправка в сеть» с `ПРОВАЛ`. Это не удобства ради: скрипт, который «случайно»
может отправить боевые деньги, опаснее скрипта, который не может ничего.

## Что именно проверяется (и почему каждый шаг стоит отдельно)

| Шаг | Что видит прогон | Что ломается в жизни, если шаг красный |
|---|---|---|
| конфигурация | `PAY_CHAIN`/`PAY_NETWORK`/контракт/RPC/подтверждения/`PAY_HOT_ADDRESS` | приём «включён», но контракт не задан → `bsc_contract_missing`, игрок отправил, мы не видим |
| адрес ↔ сеть | `PAY_HOT_ADDRESS` начинается с `0x` | форма `T…` в BSC — валидный адрес, но не наш; USDT уходят в никуда |
| нода | `chainId` = 97, `eth_blockNumber`, `decimals()` контракта |нода отвечает другую сеть — подпись с `chainId 97` там не пройдёт |
| депозит → зачисление | событие `Transfer` → `pay_chain_events` → `pay_ledger`, сумма в микро | шкала знаков: 1e18 сети против 1e6 баланса → зачисляет в миллион раз меньше |
| чужие переводы | сироты (`orphan`) и отброшенные логи | адрес игрока снят с мониторинга, деньги пришли и зависли |
| идемпотентность | второй проход зачисляет 0 | `dep:<txid>:<index>` не работает → двойное зачисление |
| покупка | `purchase`: баланс списан, право выдано, повтор ключа не списывает | списание без права, либо право без списания |
| заявка на выплату | таблица переходов `requested → approved → reserved`, `id` = `wd:<hash>:<ключ>` | заявка, созданная мимо машины состояний, не подтверждается |
| резерв | `reason=payout` в `pay_ledger`, баланс уменьшен | можно заплатить одними и теми же деньгами дважды |
| транзакция выплаты | разбор подписанного тела: `to` = контракт, `value` = 0, получатель и сумма в каллдейте, `chainId`, `nonce`, газ | каллдейт на чужого получателя = деньги ушли не игроку |
| замок nonce | два `reserveNonce` дают разные номера | параллельные отправки подписывают один nonce, вторая заявка висит в `broadcasting` |
| отправка в сеть | `txid` ноды = keccak256 нашего тела | нода приняла другое тело (расхождение в кодировании транзакции) — мы считаем, что заплатили, а сеть нет |
| квитанция | `status = 1`, глубина ≥ `confirmations` | «нет квитанции» — мемпул, а не потеря; реверт → `failed` с возвратом резерва |
| подтверждение заявки | `verifyPayout` → `confirmed`, `pay_withdrawals.status = confirmed` | форма `txid` с `0x` → `no_txid`, заявка висит вечно |
| план сбора | `evmSweepPlan`: собираемое, ниже минимума, нехватка газа, цена перевода | «сбор готов», а газа на перевод нет — план выглядит пустым |
| учёт | `остаток = зачислено − потрачено`, цепочка хешей `pay_ledger` | цифру в таблице правили в обход реестра: баланс сходится, следов нет |

## Правила чтения отчёта

- `OK` — шаг пройдёт, проверен и сошёлся.
- `ПРОПУСК` — шаг **не** проверен, причина названа. Это единственный статус,
  который нельзя перепутать с «всё хорошо»: именно на паре «скрипт зелёный /
  денег нет» теряют недели.
- `ПРОВАЛ` — расхождение. Сначала сеть и конфигурация (нода, контракт, газ),
  потом уже код: `rpc_unreachable`, `http_429`, `rpc_limited` — это провайдер, а
  не находка.
- «Отправка в сеть: была» появляется только при `--send`/`--loopback`. Флаги
  `PAYOUTS_ENABLED`/`SWEEP_ENABLED`/`POOL_ENABLED` прогон не трогает и не
  включает: решение о них — письменное, владельца.

## Известные границы прогона

- **Signer он не подменяет.** Локальный ключ в прогоне проходит те же границы
  (allowlist контракта, allowlist сети, `SIGNER_MAX_TX_MICRO`, `value = 0`), но
  это проверка того, что *мы просим подписать* правильно; сам контур подписи
  проверяется `paySignerEvm.test.ts` и живым `POST /sign/evm`.
- Реорга цепочки прогон не моделирует: курсор по блокам и `removed` в логах
  покрыты юнит-тестами, а «произошло в тестнете прямо сейчас» — нет.
- `--loopback` ничего не доказывает про доступность ноды, цены газа и лимиты
  провайдера. Он про склейку.
- Прогон поднимает свою SQLite-базу по схеме прода, но **не** читает и не пишет
  боевой D1. Проверить «наш ли курсор в проде» им нельзя.

## Что остаётся после зелёного прогона

Зелёный тестнет закрывает шаг 8 в `CHAINS.md`. Он **не** включает рельс игрокам:
переключение `PAY_CHAIN=bsc` на проде, значения `PAY_EVM_CONTRACT`/`PAY_EVM_RPC`,
и тем более `PAYOUTS_ENABLED`/`SWEEP_ENABLED` — отдельные решения владельца.
И не отменяет шаг 9: TRON удаляется только после того, как тестнет пройден и на
TRON-адресах ноль.

# Мониторинг и алерты

Цель: узнать о проблеме раньше игрока. Всё, что ниже, работает без токенов и не
трогает деньги.

## 1. Что проверяем

| Проверка | Где | Норма | Что значит отклонение |
|---|---|---|---|
| Процесс жив | `GET /health` | `200`, `ok: true` | воркер не отвечает или упал деплой |
| Сборка та | `GET /health.build` | равна `APP_BUILD` из `wrangler.toml` | задеплоено не то, что в репозитории |
| Схема платежей | `GET /pay/status.json` | `schema: "ready"`, `tables: 14` | миграции не применены, денежные маршруты вернут 503 |
| Флаги денег | там же | `payouts: false`, `sweep: false` | выплаты включились сами — останавливать, а не радоваться |
| Публичный отчёт | `GET /pool.json` | `200` | сломано чтение пула |
| Главная | `GET /` | `200` | статика не отдаётся |

Готовая проверка: `npm run health -- --base https://<домен>`.
Код выхода 1 — есть проблема, текст в stderr. Ничего не пишет и не меняет.

Аркада (десять мини-игр) проверяется отдельно и по-настоящему: `npm run
smoke:arcade -- --base https://<домен>` проходит полный круг на живом воркере —
каталог, спрайты, отказ читерского ввода, честный забег, идемпотентность сдачи,
«ASTRA не изменилась» и `reason: 'arcade'` в журнале. Код выхода 0 = раздел жив.
Подробности — `docs/ARCADE-AGENT-PROMPT.md`.

## 2. Внешний аптайм-монитор

Бесплатного минимума достаточно:

1. UptimeRobot / BetterStack → HTTP-монитор на `https://<домен>/health`,
   интервал 1 минута, keyword `"ok":true`.
2. Второй монитор на `https://<домен>/pay/status.json`, keyword `"schema":"ready"`.
3. Алерт на e-mail владельца и в Telegram (бот создаётся в 2 клика).

Почему снаружи: если воркер лежит, он сам о себе не сообщит.

## 3. Проверка из GitHub Actions (без сторонних сервисов)

`.github/workflows/health.yml` запускается каждые 30 минут и дергает
`scripts/health-check.ts` против `SITE_URL` (repository variable, по умолчанию —
рабочий адрес `workers.dev`). Падение видно в разделе Actions и в письмах GitHub.
Секретов не нужно: монитор читает только публичные маршруты.

Локальный прогон перед деплоем:

```bash
npx wrangler dev --local --port 8788
npm run health -- --base http://127.0.0.1:8788
```

## 4. Что смотреть в Cloudflare

- **Workers → Metrics**: ошибки 5xx, CPU time. Норма — 0 ошибок; CPU p99 ниже 50 мс.
- **D1 → Metrics**: строк чтения/записи. Резкий рост чтений без роста игроков —
  признак цикла в коде или бота.
- **Logs (Workers Logs)**: фильтр `error`. Скрипт логирует ошибки DO и D1.
- **Alerts → Notifications**: включить уведомления о превышении error rate.

## 5. Порог «звонить владельцу»

| Симптом | Действие |
|---|---|
| `/health` падает дольше 2 минут | смотреть деплой в Cloudflare, при необходимости `wrangler rollback` |
| `schema != ready` | `npm run db:migrate`, проверить `wrangler d1 migrations list DB --remote` |
| `payouts` или `sweep` стали `true` без команды | `POST /admin/pay/stop {stop:true}`, разобрать `pay_audit_log` |
| 5xx больше 1 % за 5 минут | логи, затем откат на предыдущую версию |
| Ответ p95 больше 1 с | проверить D1 и размер DO; см. нагрузочный тест ниже |

## 6. Нагрузка: что уже измерено

Локальный прогон (miniflare + локальная D1, 300 запросов, 20 параллельно,
маршруты `/health`, `/pay/status.json`, `/pool.json`, `/pay/products.json`,
`/pay/account.json` с токеном игрока):

```
errorRate 0, rps 215.8, p50 86.4 мс, p95 148.3 мс, p99 174.1 мс
```

Прогон без авторизации (200 запросов, 10 параллельно): `errorRate 0`,
`rps 186.4`, `p95 117.2 мс`.

**Оговорка, которую нельзя терять:** это локальная SQLite, а не продовая D1.
Сетевого хопа до D1 и лимитов Cloudflare здесь нет, поэтому цифры — нижняя
граница, а не обещание. Продовый замер нужен после появления домена:

```bash
npm run pay:loadtest -- --base https://<домен> --requests 500 --concurrency 25
# с токеном игрока добавится /pay/account.json:
npm run pay:loadtest -- --base https://<домен> --requests 500 --concurrency 25 --token "<JWT>"
```

Тест только читает: ничего не покупает и не выплачивает. Выход 1, если ошибок
больше 1 % или p95 дольше 500 мс.

Продовый прогон (`500` запросов, `25` параллельно, `crypto-astra.cryptoastra.workers.dev`):
`errorRate 0`, **p95 650–750 мс — порог 500 мс не пройден**. У замера было
известное искажение: запросы без User-Agent получали 403 от управляющих правил
Cloudflare, и часть выборок — время отказов, а не ответов. Скрипт исправлен
(`User-Agent` теперь шлёт всегда, перед замером — прогрев), но повторять замер
надо после деплоя следующей сборки. Если p95 останется выше 500 мс — это
настоящая задача, и вот её главный кандидат: `ensurePaySchema` поднимает схему
(~30 DDL-утверждений к D1 подряд) при первом запросе каждого нового изолята.
На бесплатном тарифе изолятов при 25 параллельных много, каждый греется сам, и
его «периодически переоткрываемая» D1-проверка попадает именно в хвост
распределения. Лечится переносом bootstrap в `db.batch()` или в `scheduled` —
но только по цифрам нового замера, не «на глаз».

## 7. Репетиция восстановления

`bash scripts/restore-drill.sh` выгружает D1 в SQL, разворачивает дамп в чистую
SQLite и сверяет количество строк по таблицам `users`, `world_seats`,
`pay_operations`, `pool_entries`, `pay_withdrawals`, `pay_addresses`, `pay_ledger`,
`sessions` плюс `PRAGMA integrity_check`.

Локальный прогон: дамп 12 669 байт, импорт 3 мс, `integrity: ok`, расхождений 0.
Продовый дамп проверяется той же командой:

```bash
npx wrangler d1 export DB --remote --output astra.sql
DUMP=astra.sql bash scripts/restore-drill.sh
```

Игровое состояние (ledger, корабли, гильдии) лежит в Durable Object и в дамп D1
не входит — порядок восстановления описан в `docs/RUNBOOK_BACKUP.md`.

## 8. Режимы бережливости: как сайт переживает лимит

Бесплатный план Cloudflare даёт **100 000 запросов в сутки** на весь аккаунт и
столько же запросов Durable Objects. При исчерпании Cloudflare не берёт денег —
он отвечает ошибкой 1027, и сайт недоступен до 00:00 UTC. Чтобы это не стало
сюрпризом, сервер считает свои запросы сам (`worker/src/ops/budget.ts`) и заранее
уходит в деградацию.

| Доля бюджета | Режим | Что происходит |
|---|---|---|
| < 60 % | `full` | всё работает как обычно |
| 60–80 % | `thrifty` | витрины кэшируются, пересчёты реже; блокировок нет |
| 80–95 % | `lite` | `/market`, `/guild`, `/season`, `/social`, `/ledger`, `/pool.json`, `/minigame` → `503 server_lite` |
| ≥ 95 % | `sleep` | всё, кроме входа, денег, админки и `/health`, → `503 server_sleep` + `Retry-After` до полуночи UTC |

- Режим виден в заголовке **`X-Astra-Mode`** у каждого ответа и в
  `GET /ops/status` (`mode`, `used`, `limit`, `remaining`, `retryAfter`).
- **Деньги, вход, админка и `/health` не блокируются никогда** — иначе в худший
  день нельзя было бы ни войти, ни посмотреть, что происходит.
- Счётчик намеренно приблизительный: пачка копится в памяти изолята и
  сбрасывается в D1 раз в 20 запросов или 20 секунд. Считать каждым запросом
  отдельную строку нельзя — 100 000 записей в сутки это ровно лимит D1.
- Если D1 недоступна, счётчик молчит, а запросы идут: сайт важнее статистики.
- Руководство владельца: если `/ops/status` показывает `sleep` — это не авария,
  а исчерпанный бесплатный лимит; лечится тарифом ($5/мес) или ожиданием до
  00:00 UTC.

## 9. Сон миров: почему это деньги

Durable Object стоит времени: бесплатный план даёт **13 000 GB-секунд в сутки**
на все миры. Поэтому мир просыпается только тогда, когда это нужно
(`worker/src/world/scheduler.ts`):

- служебные задачи (`ledger_verify`, `idem_cleanup`, `fuel_regen`) в тишине не
  ставят будильник — их догоняет часовой cron, а сами задачи считают пропуски
  «пачкой» (регенерация топлива начисляет все пропущенные тики, рейсы
  закрываются при пробуждении);
- играющие задачи (`expedition_finish`, `craft_finish`, `season_close`) будят мир
  всегда, даже в тишине: от них зависит то, что видит игрок;
- деятельность игрока хранится **в памяти объекта** (`lastSeen`), а не в базе:
  лишняя запись на каждый запрос съела бы суточный лимит записей;
- сверка журнала мира идёт раз в час, а не каждые пять минут.

Практический минимум: при нуле игроков мир просыпается раз в час по cron, делает
служебное и засыпает. Раньше он просыпался каждые пять минут ради сверки.

## 10. Пачка действий и очередь на клиенте

Один запрос на действие — самая дорогая привычка: бесплатный план даёт 100 000
запросов в сутки, а сессия из 25 действий съедает 25.

**`POST /batch`** (до 10 операций) выполняет игровые действия по порядку, каждое —
через тот же роутер, с тем же `Idempotency-Key` и той же проверкой прав. Что
нельзя складывать в пачку: `/pay/*` (деньги), `/auth/*` (вход), `/admin*` и сам
`/batch`. Каждая операция **тратит бюджет отдельно** — пачка не обходит лимит.

**Очередь на клиенте.** Если связь пропала или сервер ответил `503 server_sleep`,
действие не теряется: оно ложится в `localStorage` (`astra:queue:v1`, до 20 штук) и
уходит пачкой при следующей успешной загрузке состояния. Ключ идемпотентности
постоянный, поэтому повтор безопасен: сервер узнает операцию и не начислит дважды.
Ответы 5xx остаются в очереди, ответы 4xx считаются окончательными и снимаются.

Что это даёт по потолку: сессия из 25 действий при склейке по 5 — это ~8 запросов,
то есть **потолок вырастает с ~4 000 до ~12 000 сессий в сутки** без смены тарифа.

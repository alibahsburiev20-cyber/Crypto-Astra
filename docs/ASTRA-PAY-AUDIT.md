# Astra Pay Core: аудит и план (read-only)

Дата: 19.11.2026. Ветка аудита: `arena/101f66b4-crypto-astra` (от `29307b6`).
Документ отвечает на десять пунктов задания и заканчивается планом из 12 этапов с
критериями готовности. **Ничего в игре не меняется этим документом**: он только
фиксирует, что есть, чего нет и как встраивать платежи, не ломая экономику.

---

## 0. Резюме

- Игра технически готова к приёму платежей: Worker + D1 + DO + cron + CI уже
  работают, есть Ledger с хеш-цепочкой, идемпотентность, аудит и публичный отчёт.
- Платёжного кода **нет вообще**: ни одной строки про TRON, USDT, депозиты,
  выплаты, Queues или Signer. `pool_entries` — ручной учёт денег, а не приём.
- Три жёстких блокера, и ни один не решается кодом:
  1. **Юридический.** Кастодиальный пул с выплатами в ЕС — это, вероятнее всего,
     лицензия (BaFin), KYC/AML и налоговый учёт. До заключения юриста реальные
     деньги включать нельзя.
  2. **Ключи.** Cloudflare Worker Secrets — не HSM. Хот-кошелёк, ключи которого
     живут в аккаунте Cloudflare, при компромате аккаунта теряется целиком.
     Нужен отдельный контур подписи и/или on-chain мультисиг.
  3. **Инфраструктура.** Cloudflare Queues доступны только на платном плане
     ($5/мес). Мониторинг блокчейна раз в минуту на бесплатном плане упирается в
     лимиты запросов.
- Предлагаемый порядок: сначала **только приём и учёт** (депозиты, магазин,
  ручная выдача), потом **выплаты** — и только после Production Gate.

## 1. Что уже реализовано

### Рантайм и инфраструктура

| Компонент | Факт | Путь |
|---|---|---|
| Worker | один скрипт `crypto-astra`, роутер на ~40 путей, статика через `[assets]` | `worker/src/index.ts`, `worker/src/http/router.ts` |
| D1 | `astra-global`, 7 таблиц, миграции 0001–0006 | `wrangler.toml`, `worker/migrations/d1` |
| D1 preview | отдельная база `astra-preview`, свои DO | `[previews.*]` |
| Durable Objects | `World` (SQLite мира, 27 таблиц) и `WorldLobby` | `worker/src/world/World.ts`, `worker/src/lobby/WorldLobby.ts` |
| Cron | `0 * * * *` и `0 3 * * *`: пинание миров, архив, чистка сессий и лимитов | `worker/src/index.ts` |
| CI/CD | GitHub Actions (unit, e2e на `wrangler dev`, typecheck, lint) + Cloudflare Workers Builds на `main` | `.github/workflows` |
| Тесты | 228 unit в 31 файле, 24 e2e | `worker/test` |

### Аутентификация и доступ

- JWT HS256 на 15 минут (`sub`, `w`), refresh 30 дней с ротацией и отзывом всех
  сессий при повторном использовании; в D1 только SHA-256 refresh-токена
  (`worker/src/auth/*`).
- Пароли: PBKDF2-HMAC-SHA256, 100 000 итераций, соль 16 байт.
- Лимиты частоты: `auth_limits` в D1, только для `/auth/login` и `/auth/register`.
- Turnstile на регистрации и после трёх неудачных входов.
- Админ-доступ: **единственный** `X-Admin-Token` для записи пула. Поле
  `ADMIN_ACCESS_AUD` в `Env` объявлено, но Cloudflare Access **не реализован**.

### Игровой Ledger и экономика

- `ledger` в SQLite мира: append-only (триггеры), хеш-цепочка
  `hash = SHA-256(prev_hash + каноническая запись)`, ежедневная сверка
  `ledger_checks`, при расхождении мир замораживается (`world_frozen`, 423).
- Идемпотентность: `withIdempotency` внутри транзакции DO, ключ уникален в
  пределах игрока, тело хешируется.
- Активы: `astra`, `fuel`, `points`, `res:<имя>`, `xp`, `dur:<ship>`. ASTRA —
  внутриигровая валюта, продажи и вывода нет.
- Экономика проверена симуляцией: поглощение 72.4–83.2 % в зависимости от среза.

### Astra Pool (то, что уже есть)

- `pool_entries` в D1: `kind` (`in`/`out`/`ops`), суммы **в центах EUR/USD**,
  `CHECK currency IN ('EUR','USD')`, уникальный `ref`, append-only триггеры,
  публичная заметка, сезон.
- Серверный расчёт: резерв 20 % (`POOL_FEE_BP = 2000`), призовой фонд, остаток;
  валюты не складываются (`worker/src/pool/accounting.ts`).
- Публичный отчёт: `/pool.html` + `/pool.json` (+ алиас `/pool/report`), без
  входа и без `ref`/`id`; флаг `payoutsEnabled: false`.
- Запись: `POST /admin/pool/entry` с `X-Admin-Token`; идемпотентность по `ref`.
- Схема самолечится при первом обращении (`worker/src/db/bootstrap.ts`), потому
  что деплой идёт из браузера и `wrangler d1 migrations apply --remote` недоступен.

### Клиент

- SPA-игра (`client/app.js`, ~2 000 строк) и лендинг; CSP без `unsafe-inline`,
  `connect-src 'self'` — **любые** обращения к TronGrid из браузера невозможны
  без изменения CSP, и это правильно: блокчейн трогает только сервер.
- Страница пула — статический HTML + `pool.js`, только форматирование чисел.

## 5. Целевая архитектура

```
Клиент ── /pay/* ──► Worker (API, JWT)
                        │
                        ├─ D1: users, pay_* (учёт, счета, заявки)
                        ├─ Queue deposits ──► consumer: проверка и зачисление
                        ├─ Queue payouts  ──► consumer: резерв → signer → broadcast
                        ├─ Cron (1 мин): TronGrid → solid-блоки → Queue
                        └─ Service binding ──► Signer Worker (только подпись)
                                                  │
                                                  ├─ ключи в Secrets (не в D1/гите/клиенте)
                                                  ├─ allowlist контрактов/адресов/сумм
                                                  └─ лог каждой подписи
TronGrid (индексатор) + Solidity API (финальность) ◄── monitor
```

Модули (как просили, отдельными папками):

```
worker/src/pay/
  tron/            адреса, base58, ABI Transfer, клиент TronGrid/Solidity
  addresses/       HD-деривация, выдача адреса, привязка к игроку
  monitor/         блоки, события, дедуп (txid,event_index), восстановление
  deposits/        сопоставление, недоплата/переплата, ручная проверка
  ledger/          pay_ledger, компенсирующие операции, сверка
  pool/            pay_pool_cycles, доступный фонд, лимиты
  payouts/         заявки, резерв, статусы, повторы, DLQ
  signer-client/   typed RPC к Signer Worker
  reconciliation/  ежедневная сверка D1 ↔ блокчейн ↔ казна
  admin/           Access-guard, действия, аудит
  flags.ts         шесть переключателей + проверка окружения
```

## 6. Схема D1 (проект, 14 таблиц)

Все суммы — `INTEGER` в минимальных единицах USDT (1 USDT = 1 000 000).
`float` и `REAL` не используются. Время — unix ms. Никаких `ON DELETE CASCADE`:
историю не удаляем.

| Таблица | Ключевые поля | Инварианты |
|---|---|---|
| `pay_addresses` | `id`, `user_id`, `address` (base58), `hex`, `derivation_index`, `created_at`, `active` | `address` UNIQUE, `derivation_index` UNIQUE, `user_id` UNIQUE (один постоянный адрес) |
| `pay_invoices` | `id`, `user_id`, `product_id`, `amount_micro`, `status`, `address`, `created_at`, `expires_at`, `paid_at`, `deposit_txid` | один активный счёт на игрока: частичный UNIQUE-индекс по `status='open'` |
| `pay_chain_blocks` | `height`, `block_id`, `parent_id`, `solidified_at`, `processed_at` | PK `height`; пропуск высоты — авария, а не норма |
| `pay_chain_events` | `txid`, `event_index`, `block_height`, `from_addr`, `to_addr`, `contract`, `amount_micro`, `status`, `raw` | PK `(txid, event_index)`; фильтр контракта на записи |
| `pay_deposits` | `id`, `txid`, `event_index`, `user_id`, `amount_micro`, `confirmations`, `status` (`detected`/`confirmed`/`credited`/`manual`/`ignored`), `credited_at` | UNIQUE `(txid, event_index)`; `credited` без записи в `pay_ledger` невозможен (проверка в одной транзакции) |
| `pay_ledger` | `id`, `user_id`, `asset` (`USDT`), `delta` (со знаком), `reason` (`deposit`/`purchase`/`payout`/`fee`/`adjust`), `source_ref`, `idem_key`, `created_at` | append-only триггеры; UNIQUE `idem_key`; баланс = сумма `delta`, проверяется сверкой |
| `pay_products` | `id`, `kind` (`cosmetic`/`premium`/`service`), `title`, `price_micro`, `catalog_json`, `enabled`, `season_id` | цена целым числом, без скидок-флоатов |
| `pay_entitlements` | `id`, `user_id`, `product_id`, `purchase_id`, `granted_at`, `expires_at`, `payload` | UNIQUE `(user_id, purchase_id)`; выдача идемпотентна |
| `pay_pool_cycles` | `id`, `period_start`, `period_end`, `confirmed_in`, `ops_reserved`, `prize_budget`, `reserved`, `paid`, `status` | один открытый цикл; `prize_budget = confirmed_in - ops_reserved` |
| `pay_withdrawals` | `id`, `user_id`, `address`, `amount_micro`, `fee_micro`, `status` (`requested`/`approved`/`reserved`/`broadcasting`/`sent`/`confirmed`/`failed`/`manual`), `idem_key`, `created_at`, `decided_at`, `txid` | UNIQUE `idem_key`; переходы только по разрешённой таблице состояний; `txid` UNIQUE |
| `pay_payouts` | `id`, `withdrawal_id`, `attempt`, `txid`, `signed_at`, `broadcast_at`, `solidified_at`, `result`, `error` | UNIQUE `(withdrawal_id, attempt)`; новый attempt только после явного `failed`/`manual` |
| `pay_treasury` | `id`, `kind` (`hot`/`cold`/`deposit`), `address`, `balance_micro`, `energy`, `bandwidth`, `trx_micro`, `updated_at` | фактический баланс только из блокчейна, не из наших расчётов |
| `pay_operations` | `idem_key`, `scope`, `user_id`, `request_hash`, `response`, `created_at` | UNIQUE `(scope, idem_key)`; ответ возвращается повторно |
| `pay_audit_log` | `id`, `actor`, `action`, `target`, `payload`, `created_at` | append-only; пишется и админом, и автоматикой |

Дополнительно: `pay_sweeps` (консолидация) можно сделать как `pay_operations` +
`pay_payouts` с `kind='sweep'`, отдельная таблица не обязательна.

**Сверка.** Ежедневная задача сравнивает: (а) сумму `pay_ledger` по игроку с
суммой `credited` депозитов минус `payout`; (б) `pay_treasury.balance_micro` с
фактическим балансом USDT в блокчейне; (в) отсутствие `confirmed` депозитов без
записи в Ledger. Любое расхождение — стоп-флаг `PAYOUTS_ENABLED=false` и алерт.

## 7. Blockchain Monitor

- **Сеть:** TRON Mainnet, USDT TRC-20
  `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`, decimals 6.
- **Источник:** TronGrid (`/v1/events` по контракту, `only_confirmed=true`) +
  Solidity API (`walletsolidity/getnowblock`, `walletsolidity/gettransactioninfobyid`)
  для финальности. Отсутствие события у индексатора — **не доказательство**
  отсутствия платежа: раз в сутки адреса досматриваются по `trc20/transactions`
  и по фактическому балансу.
- **Идентификатор события:** `(txid, event_index)`, где `event_index` — позиция
  лога в receipt (сверять с полем API; если поля нет — индекс массива `log[]`).
- **Проверки до зачисления:** контракт = USDT; `to` = адрес игрока; `from` ≠
  системные адреса; сумма > 0 и кратна 1; транзакция `ret[0].contractRet = SUCCESS`;
  блок solidified; адрес принадлежит активному игроку.
- **Восстановление:** курсор `last_solidified_height` в `pay_chain_blocks`;
  при пропуске высоты — добор с прошлой известной; Queue с DLQ и повторами;
  «застрявшие» депозиты старше N минут — в ручную проверку.
- **Нельзя:** зачислять по «кнопке Проверить оплату», доверять сумме из клиента,
  считать платёж подтверждённым по `latest` блоку.

## 8. Financial Ledger и Pool Engine

- Отдельный `pay_ledger`, не связанный с игровым Ledger мира. ASTRA и USDT не
  конвертируются нигде.
- `Available = Confirmed − Reserved − Paid − Locked` (как в задании), плюс
  `ops_reserved` (20 %) — отдельной строкой, чтобы формула была проверяемой.
- Резерв: заявка переводит сумму в `reserved` в **той же транзакции**, что и
  проверка доступного фонда; повторный запрос с тем же `idem_key` возвращает тот
  же резерв.
- Лимиты: на выплату, в сутки и в месяц; отдельный «холодный» лимит, выше
  которого — ручное подтверждение. Аварийный стоп — флаг + отдельная запись в
  `pay_audit_log`.
- Комиссии сети списываются из пула (`fee_micro`) и видны в отчёте отдельно.
- Повторная выплата невозможна: `txid` UNIQUE, `withdrawal_id` UNIQUE в
  `pay_payouts` на attempt, а новый attempt — только из состояния `failed`.
  При «потере ответа после broadcast» статус `broadcasting` и **только** сверка с
  блокчейном решает, был ли перевод; автоматический повтор запрещён.

## 9. Signer: как это сделать в Cloudflare-only

**Факт:** Cloudflare Worker Secrets шифруются at rest и расшифровываются в
изоляте, но это не HSM и не аппаратный кошелёк. Ключ, доступный коду Worker'а,
доступен и любому, кто получил контроль над аккаунтом/деплоем. Поэтому
«изоляция» — это в первую очередь **отдельный контур и мультисиг**, а не Secrets
сами по себе.

Три варианта, по возрастанию надёжности:

1. **Отдельный Signer Worker** (`astra-pay-signer`, другой деплой, другие
   Secrets, без публичного маршрута, только service binding из основного
   Worker'а). Внутри: allowlist контракта USDT, allowlist адресов (казна +
   подтверждённые заявки), лимит на транзакцию, TTL задания, запись каждой
   подписи. Ключи депозитного контура и казны **разные** и в основном Worker'е
   отсутствуют. Дешево, быстро, но при компромате аккаунта Cloudflare ключи
   уходят вместе с ним.
2. **Signer вне Cloudflare** (VPS/сервер + HSM или KMS с secp256k1, либо
   аппаратный кошелёк с ручным подтверждением крупных выплат). Основной Worker
   обращается к нему по mTLS/подписи запроса. Это единственный вариант, где
   компромат Cloudflare не равен потере средств.
3. **On-chain мультисиг TRON** (permissions `active`: 2 из 3 ключей — Cloudflare,
   ваш аппаратный, резервный бумажный). Даже вариант 1 становится безопаснее:
   одна угнанная ключевая доля не двигает средства. Рекомендую **1 + 3** для
   старта и переход к **2** при росте сумм.

Что нельзя делать ни в одном варианте: хранить приватные ключи в D1, GitHub,
переменных `[vars]`, клиентском коде или localStorage; подписывать произвольные
транзакции по запросу из интернета; иметь один ключ и для депозитов, и для казны.

## 10. Риски

| Риск | Вероятность | Последствие | Что делаем |
|---|---|---|---|
| Юридический: кастодиальный пул + выплаты без лицензии/KYC | высокая | остановка проекта, штрафы | не включать реальные выплаты до заключения юриста; на первом этапе — только приём и ручная выдача |
| Компрометация ключей в аккаунте Cloudflare | средняя | потеря казны | мультисиг + отдельный контур; лимиты; холодная казна; ротация |
| Двойное зачисление из-за повторов Queue (at-least-once) | высокая без защиты | эмиссия «из воздуха» | PK `(txid,event_index)`, UNIQUE `idem_key`, зачисление в одной транзакции с записью Ledger |
| Двойная выплата при «потере ответа» | средняя | потеря денег | состояния `broadcasting`/`manual`, сверка по txid, запрет авто-повтора |
| Отставание индексатора | средняя | игрок «не видит» платёж | вторичный досмотр по адресу и балансу, ручная очередь, SLA-алерт |
| Энергия/TRX на депозитных адресах | высокая | невозможность sweep, зависшие средства | держать минимальный TRX-буфер, делегировать энергию со стейка, алерт по балансу |
| Лимиты D1/Free-плана | высокая | отказ записи после исчерпания суточной квоты | Workers Paid + батчи + не писать каждый опрос |
| Ответственность за «инвестиции» и обещания дохода | средняя | претензии, блокировка рекламы | формулировки как в `POOL.md`: не инвестиция, дохода не гарантируем |
| Мультиаккаунты и фарм пула | высокая | слив фонда | KYC при выплатах, лимиты на аккаунт/IP/устройство, антифрод-флаги |
| Санкции/AML | средняя | блокировка провайдера | скрининг адресов, ручная проверка крупных |
| Cloudflare ToS для финансовых сервисов | средняя | блокировка аккаунта | прочитать и, если нужно, согласовать с поддержкой до запуска |
| Ошибка в арифметике (float) | низкая | копейки/центы не сходятся | только целые, тесты на суммы-«ловушки» (2^53, переполнение) |

## 13. Особые решения, которые предлагаю (и обоснование)

1. **Не менять `pool_entries`.** Это рабочий фиатный учёт с публичным отчётом.
   USDT идёт в `pay_ledger`, отчёт показывает два блока.
2. **Один активный счёт на игрока** (как разрешено в задании). Новый счёт
   закрывает предыдущий; адрес при этом остаётся тем же и постоянным.
3. **Первая версия магазина — без Premium-подписки**: только косметика и
   разовые услуги. Подписка — это отдельный юридический и биллинговый контур.
4. **Выплаты — только вручную подтверждённые на старте** (кнопка админа +
   лимит), автоматика включается после 2 недель сверки без расхождений.
5. **Тестнет TRON (Nile)** для этапов 5–10: реальная сеть только на этапе 12,
   чтобы не платить за энергию во время отладки.

## 17. Как это делается без денег

Аудит исходил из того, что на старте можно потратить $5–20. Если бюджета нет
вообще, план остаётся рабочим — меняются только инструменты:

| Что было в плане | Замена без денег | Что теряем |
|---|---|---|
| Cloudflare Queues | таблица-очередь в D1 (`pay_chain_events.status = 'pending'`) + cron | задержку в минуту вместо секунд |
| Workers Paid (CPU) | Free: короткие запросы, тяжёлое — в cron пачками | нельзя считать большие выборки в одном запросе |
| TronGrid с ключом | бесплатный ключ без карты + свой лимит опроса | чаще `429`, опрос реже |
| Mainnet и энергия TRX | тестнет **Nile**: тестовые TRX и USDT бесплатно | реальные платежи не принимаются |
| Юрист сейчас | флаги `off` и никаких обещаний дохода | запуск денег ждёт заключения |

Итог: **этапы 1–10 можно сделать полностью бесплатно** в тестнете. Деньги
начинаются только на этапе 11–12 (`mainnet`), и к тому моменту решение можно
принимать заново — уже с работающей системой на руках. Единственная реальная
трата на mainnet — активация адресов и энергия переводов: единицы TRX, то есть
центы, и только когда появится первый платящий игрок.
